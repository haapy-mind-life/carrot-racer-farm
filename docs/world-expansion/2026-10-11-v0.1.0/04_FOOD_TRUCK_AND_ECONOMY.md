# 04. 푸드트럭 장사·음식·별코인 계약 초안

> **REQUEST + PROPOSED**. 메뉴 이름은 사용자 요청 그대로 보존한다. 아래 가격·거래 규칙은 검토 후보이며, 현재 코드에 적용되지 않았다.

## 현준이의 필수 메뉴

| ID | 이름 | 구별 요소(제안) | 상태 |
| --- | --- | --- | --- |
| FOOD-01 | 돈까스 | 커다란 바삭 돈까스 접시 | REQUEST |
| FOOD-02 | 김치 | 빨간 김치 접시 | REQUEST |
| FOOD-03 | 피자 | 일반 크기 조각 또는 한 판 | REQUEST |
| FOOD-04 | 콜라 | 컵/음료수 | REQUEST |
| FOOD-05 | 대왕 피자 | 일반 피자보다 확실히 크게 보이는 피자 | REQUEST |
| FOOD-06 | 엄청 큰 황금 피자 | 대왕 피자보다 화려한 큰 황금 장식/빛 효과 | REQUEST |
| FOOD-07+ | 여러 초대형 특별 메뉴 | 현준이 선택을 받기 전 제안 목록만 별도 관리 | OPEN |

### 특별 메뉴 추가 아이디어 (아직 사용자 승인 아님)

- 대왕 치즈 피자, 공룡 도시락, 초대형 과일 주스, 무지개 아이스크림, 별빛 햄버거.
- 원한 것이 '엄청 큰 음식'이라는 느낌이므로, 단순 글씨가 아니라 **접시·트럭·캐릭터 대비 물리적인 크기 차이**를 확인한다.
- 식품명은 아동 놀이용 가상 음식이다. 외부 실물 메뉴 주문 또는 현금 결제 기능은 포함하지 않는다.

## 실제 게임의 재화

- **FACT:** 현재 `src/lib/world-model.ts`의 `GameState.money`는 '별코인'이다.
- **PROPOSED:** 푸드트럭 수익은 동일한 **별코인 잔액**에 합산한다. 병렬 '현금 지갑'을 새로 만들지 않는다.
- **OPEN:** 메뉴별 판매 가격·재료비·보상·재고·손님 등장 빈도·별코인 소비처.
- **제안:** 최초 구현은 부담 없는 주문 확인→판매→결과가 보이는 가벼운 방식. 재료 구매·시간 압박·실패 벌점·랜덤 유료 뽑기는 후순위.

## 동일 월드에서 한 번의 판매가 성립하는 조건

1. 현준이가 실제 푸드트럭 위치에 접근한다.
2. 손님 NPC가 어떤 음식을 원하는지 말한다. 어린이가 읽기 쉬운 아이콘/큰 이름 동시 표시.
3. 메뉴를 고르고 음식 모습이 나타난다. 조리가 필요할지, 손에 든 채 전달할지는 OPEN.
4. 손님에게 음식이 전달되면 판매 성공이 보이고 공용 별코인이 **한 번만** 늘어난다.
5. 현준이가 잠수함·집·러너로 이동해도 별코인 잔액과 진행기록이 보존된다.

## 상태/저장 계약 제안 (코드 인터페이스 확정 아님)

| 엔티티 | 최소 필드 후보 | 의미 / 수명 |
| --- | --- | --- |
| `FoodItem` | `id`, `label`, `displayScale`, `price` | 메뉴 버전 관리; 가격은 양의 정수·상한 |
| `FoodOrder` | `orderId`, `foodId`, `customerId`, `status` | `offered → accepted → prepared → served / cancelled` |
| `SaleLedger` | `transactionId`, `orderId`, `amount`, `completedAt` | 성공 매출 중복 방지 근거; PII 없음 |
| `Wallet` | 현행 `GameState.money` 연동 | 수익/지출 단일 원장 |
| `HeldItem` | `foodId`, `origin`, `pose` | 음식 집기·들고 이동·먹기 표시, 세션 또는 저장 정책 OPEN |
| `TruckState` | `truckId`, `parkedAt`, `isOpen` | 트럭 주차/영업 제어, 영속 범위 OPEN |

**중요:** 기존 `GameState.version=2`와 `hyunjun-game-v2`의 저장 데이터는 그대로 읽혀야 한다. 별코인 재사용 시 기존 `money` 필드를 삭제하거나 재정의하지 않는다. 저장 버전 승격/선택 저장 키/마이그레이션은 기술 검토에서 결정.

### 오류·중복/복구 기대

| 사건 | 기대되는 사용자 경험 | 데이터 계약 |
| --- | --- | --- |
| 판매 버튼 더블탭 | 음식·별코인 한 번만 지급 | 동일 `orderId/transactionId` 재처리 거부 |
| 돈 없는 손님/유효하지 않은 음식 | 부드러운 안내, 추가 지급 없음 | 알려진 메뉴·상태인지 검사 |
| 판매 중 맵 이동/취소 | 미완료 주문을 취소하거나 안전하게 복귀 | 불완전 거래에 매출 지급 없음 |
| 저장소 접근 불가 | 현 세션 계속, 저장 경고 노출 | 성공 저장으로 거짓 표시 금지 |
| 저장 중 새로고침 | 기존 별코인·완료 거래와 일관성 유지 | reducer 원자적 변경 / 멱등성 |
| 푸드트럭 여러 번 열기 | 이전 주문을 임의 복제하지 않음 | 주문 상태/신규 ID |
| 저장 데이터 손상 | 기존 복구 정책과 호환 | 범위/형태 검사, 회복 가능 경고 |

## 결정해야 할 비즈니스 규칙

- 가격표는 사용자 선택을 우선한다. 승인 전 테스트 용 가격은 **실제 기준으로 고정하지 않는다.**
- 푸드트럭이 움직이는 자동차인가, 마을에 고정된 상점인가, 둘 다 가능한가?
- 조리·음식 집기·손님 전달을 세 단계로 나눌 것인가? 너무 많은 메뉴를 눌러야 하는 문제는 피해야 한다.
- 가정의 음식 먹기와 푸드트럭 판매 음식 데이터를 공유할지 분리할지?
- 황금 피자는 꾸미기 아이템인가, 고액 장사 상품인가? 실제 현금성 대가와 연동하지 않는다.
